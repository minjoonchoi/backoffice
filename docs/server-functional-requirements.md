# Backoffice 서버 기능 요구사항

## 1. 문서 정보

| 항목             | 내용                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| 문서 목적        | 백오피스의 데이터 모델, 권한 판정, 상태 전이, 무결성, 영속 저장, 감사 및 외부 연동 규칙을 정의한다. |
| 대상 사용자      | 백엔드 개발자, 프런트엔드 개발자, 아키텍트, 보안 담당자, QA 담당자                                  |
| 기준일           | 2026-08-12                                                                                          |
| UI 기능 요구사항 | [Backoffice UI 기능 요구사항](ui-functional-requirements.md)                                        |

이 문서는 클라이언트 구현과 관계없이 서버가 보장해야 하는 업무 규칙의 원본이다. 클라이언트가 동일 규칙을 선검증하더라도 서버는 인증된 요청 주체와 최신 데이터를 기준으로 다시 판정한다.

상태는 다음과 같이 구분한다.

- `로컬 검증`: 현재 local API/domain 계층에서 규칙을 검증한다. 운영 서버 구현 완료를 의미하지 않는다.
- `후속`: 규칙은 확정되었으나 현재 local 계층에서도 전체 흐름을 제공하지 않는다.
- `외부 연동`: 운영 환경의 인증, 데이터베이스 또는 외부 시스템 구현이 필요하다.

서버 요구사항 ID는 UI 문서의 도메인 prefix에 `S`를 추가한다. 예를 들어 `USR-S001`은 사용자 서버 규칙이며 관련 UI 요구사항에서 이 ID를 참조한다.

## 2. 공통 서버 요구사항

| ID       | 상태      | 요구사항                                                                                                                                                                                                |
| -------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| COM-S001 | 로컬 검증 | 모든 command 입력은 신뢰하지 않고 스키마로 검증해야 한다. 실패는 구분 가능한 오류 코드로 반환하고 예외를 성공으로 변환하거나 무시하지 않아야 한다.                                                      |
| COM-S002 | 외부 연동 | 운영 데이터는 데이터베이스에 영속 저장하고 생성·수정·삭제·권한 부여·회수의 주체, 대상, 시각과 결과를 감사 로그로 남겨야 한다.                                                                           |
| COM-S003 | 로컬 검증 | 인증 사용자와 직접·조직·역할·그룹 경유 활성 정책을 기준으로 UI 리소스와 업무 command 권한을 서버에서 검증해야 한다. 권한 정보가 없거나 불완전하면 허용하지 않아야 한다.                                 |
| COM-S004 | 로컬 검증 | 사용자·조직·역할·그룹 관계는 중복 저장하지 않아야 하며 연결과 제거 command는 대상 존재 여부와 보호 관계를 검증해야 한다.                                                                                |
| COM-S005 | 후속      | 목록 query는 허용된 컬럼 조건, 정렬과 최대 20개 단위 페이지네이션을 제공하고 권한 범위가 적용된 전체 개수를 함께 반환해야 한다.                                                                         |
| COM-S006 | 로컬 검증 | 요청 제출, 승인, 정책 부여·회수, 리소스 생성·폐기와 자격증명 등록 이벤트는 대상 사용자별 알림으로 생성하고 최신 순 조회가 가능해야 한다. 운영 서버는 중복 이벤트 방지와 읽음 상태를 함께 관리해야 한다. |
| COM-S007 | 후속      | 상태를 변경하는 command는 트랜잭션 경계를 가져야 하며 재시도 또는 동시 요청으로 같은 결과가 중복 생성되지 않도록 멱등성 또는 충돌 검사를 제공해야 한다.                                                 |
| COM-S008 | 외부 연동 | 운영 서버는 인증 공급자의 세션을 검증해 내부 사용자와 연결해야 한다. 유효하지 않은 세션, 퇴직 사용자 또는 알 수 없는 사용자는 보호 리소스에 접근할 수 없어야 한다.                                      |
| COM-S009 | 로컬 검증 | 서버는 프런트엔드 URL을 권한 식별자로 저장하지 않고 네임스페이스와 안정적인 UI 리소스 key를 사용해야 한다. 경로 변경은 권한 데이터 변경을 요구하지 않아야 한다.                                         |

### 2.1 홈 집계

| ID       | 상태      | 요구사항                                                                                                                                                                                                          |
| -------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HOM-S001 | 로컬 검증 | 홈 query는 현재 사용자의 실효 접근 정책, 본인이 요청했거나 소속 조직이 관리하는 자격증명과 현재 사용자가 처리할 수 있는 승인 대기 요청만 집계해야 한다. 각 집계의 상세 목록에도 동일한 권한 범위를 적용해야 한다. |
| HOM-S002 | 로컬 검증 | 알림 읽음 command는 알림 소유 사용자와 UI 기능 권한을 검증하고 읽음 시각을 저장해야 한다. 이미 읽은 알림에 대한 반복 command는 같은 결과를 반환해야 한다.                                                         |

## 3. IAM 데이터와 권한

### 3.1 공통 관계

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                             |
| -------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IAM-S001 | 로컬 검증 | 사용자와 조직은 다대다 관계다. 재직·휴직 사용자는 하나 이상의 조직에 소속되고 퇴직 사용자만 무소속일 수 있다.                                                                                                                                        |
| IAM-S002 | 로컬 검증 | 조직은 하나의 상위 조직과 여러 하위 조직을 가질 수 있으며 자기 자신 또는 하위 조직을 상위로 지정하는 순환 관계를 허용하지 않아야 한다.                                                                                                               |
| IAM-S003 | 로컬 검증 | 역할은 사용자·조직과 각각 다대다 관계이며 직접 부여와 조직 경유 역할을 구분할 수 있어야 한다.                                                                                                                                                        |
| IAM-S004 | 로컬 검증 | 그룹은 사용자와 다대다 관계이며 시스템 그룹은 해당 그룹의 동기화 규칙 외의 일반 관계 command로 변경할 수 없어야 한다.                                                                                                                                |
| IAM-S005 | 로컬 검증 | 모든 사용자에게 `Backoffice 일반 사용자` 역할을 자동 부여하되 IAM 리소스는 포함하지 않아야 한다. IAM 조회·관리 기능과 그 외 전문 운영 기능은 메뉴별 역할 하드코딩이 아니라 역할에 연결된 유형별 정책으로 관리해야 한다.                              |
| IAM-S006 | 로컬 검증 | 사용자 조회 시 직접·조직 경유 역할, 소속 조직과 그룹을 구분해 반환하고 유효 역할과 정책을 계산할 수 있어야 한다.                                                                                                                                     |
| IAM-S007 | 로컬 검증 | 시스템 기본 `Backoffice IAM 운영자` 역할은 사용자·조직·역할·그룹의 메뉴, 목록·상세 view와 관리 action을 하나의 UI 접근 정책으로 제공해야 한다. 로컬 fixture에서는 개발 1팀에 이 역할을 부여하고 시스템 관리자 역할은 David에게만 직접 부여해야 한다. |

### 3.2 사용자

| ID       | 상태      | 요구사항                                                                                                                                                                                                                          |
| -------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| USR-S001 | 로컬 검증 | 사용자는 2~40자의 중복되지 않는 닉네임, 최대 160자의 유효하고 중복되지 않는 이메일, `employed`·`on-leave`·`resigned` 재직 상태와 중복 없는 최대 20개 조직 식별자를 가진다. 사번은 저장하지 않는다.                                |
| USR-S002 | 로컬 검증 | 사용자 query는 IAM 조회 UI 리소스 권한을 검증해야 하며 권한이 없는 일반 사용자에게 사용자 데이터를 반환하지 않아야 한다. IAM 운영자와 Backoffice 시스템 관리자는 퇴직 사용자를 포함해 운영에 필요한 범위를 조회할 수 있어야 한다. |
| USR-S003 | 로컬 검증 | 재직·휴직 사용자의 무소속 생성, 마지막 조직 제거와 무소속 퇴직자의 재직·휴직 변경을 거부해야 한다. 관계·상태 변경은 권한을 검증해야 한다.                                                                                         |
| USR-S004 | 후속      | 조직·역할·그룹 관계를 회수할 때 활성 요청 템플릿의 고정 담당자와 진행 중 요청에 미치는 영향을 검증해야 한다.                                                                                                                      |
| USR-S005 | 로컬 검증 | 사용자 상세 query는 사용자가 작성한 요청과 그 요청에서 생성된 현재·과거 자격증명을 요청일 역순으로 반환할 수 있어야 한다.                                                                                                         |
| USR-S006 | 로컬 검증 | 조직 관계 제거 전후의 유효 역할·실효 정책·자격증명 조회 범위를 같은 권한 계산 규칙으로 비교해 영향을 반환해야 한다.                                                                                                               |

| ID       | 상태      | 요구사항                                                                                                                         |

| ORG-S003 | 로컬 검증 | 조직장 관계는 일반 사용자 제거 command로 제거할 수 없고 조직 수정 시 계층 순환과 조직장 재직 상태를 다시 검증해야 한다.          |

| ORG-S005 | 로컬 검증 | 조직 상세 query는 조직에 직접 부여된 정책, 조직이 소유한 서비스와 그 서비스에 등록된 자격증명을 반환할 수 있어야 한다.           |

### 3.4 역할

| ID       | 상태      | 요구사항                                                                                                                                      |
| -------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| ROL-S001 | 로컬 검증 | 역할은 2~~80자의 대소문자 비구분 고유 이름, 2~~500자의 설명, 직접 부여 사용자와 조직 관계를 가진다. 시스템 기본 역할을 식별할 수 있어야 한다. |
| ROL-S002 | 로컬 검증 | 역할 query는 직접 부여 사용자·조직과 역할에 직접 부여된 정책을 반환해야 한다.                                                                 |
| ROL-S003 | 로컬 검증 | 역할 생성 UI 리소스 권한을 가진 Backoffice 시스템 관리자·IAM 운영자만 역할을 생성할 수 있어야 한다.                                           |
| ROL-S004 | 로컬 검증 | 시스템 기본 역할은 수정·삭제할 수 없고 일반 역할 삭제 전 사용자·조직·정책·네임스페이스 관리자 관계가 없음을 검증해야 한다.                    |
| ROL-S005 | 로컬 검증 | 역할 정책 부여·회수 command는 UI 기능 권한, 대상·활성 정책 존재와 중복을 검증하고 네임스페이스 관리자 필수 정책의 회수를 거부해야 한다.       |

기본 역할은 `Backoffice 시스템 관리자`, `Backoffice 정책 운영자`, `Backoffice IAM 운영자`, `Backoffice 일반 사용자`, `Backoffice UI 리소스 관리자`다. `Backoffice 시스템 관리자`는 Backoffice 네임스페이스의 관리자 역할이며 다른 네임스페이스의 관리자 역할과 구분한다.

| GRP-S002 | 로컬 검증 | 그룹 생성 UI 리소스 권한을 가진 Backoffice 시스템 관리자·IAM 운영자만 일반 그룹을 생성할 수 있어야 한다.                                                         |

## 4. 요청 템플릿

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TPL-S001 | 로컬 검증 | 템플릿은 고유 이름, `access-policy`·`credential` 분류, 분류에 맞는 처리 유형, 활성 상태, 처리 단계와 입력 항목을 가진다. 비활성 템플릿은 새 요청에 사용할 수 없어야 한다.                                                                                                                                                                                                |
| TPL-S002 | 로컬 검증 | 실행 단계는 1~12이며 첫 단계는 1, 이후 단계는 같은 번호 또는 1 증가만 허용한다. 같은 실행 단계는 병렬로 해석하고 단계 유형은 요청·승인·합의·참조만 허용한다.                                                                                                                                                                                                             |
| TPL-S003 | 로컬 검증 | 입력 항목은 최대 30개, 템플릿 안에서 고유한 소문자 kebab-case key, 표시 이름, 필수 여부와 입력 방식을 가진다. 시스템 연결 값은 종류별 하나만 허용하며 발급 템플릿은 서비스·요청 조직·자격증명 이름·요청 사유를, 교체·폐기 템플릿은 요청 조직·사유를 필수로 가진다.                                                                                                       |
| TPL-S004 | 로컬 검증 | 고정 사용자·조직은 템플릿 저장 시 검증하고 요청자, 작성 시 선택 사용자, 요청 조직장·조직과 대상 서비스 소유 조직은 요청 제출 시점의 최신 데이터로 확정해야 한다. 요청자가 요청 조직의 조직장이면 자신이 아닌 재직 조직장이 발견될 때까지 상위 조직을 탐색하며, 유효한 승인자를 찾지 못하면 제출을 거부해야 한다. 모든 담당자는 재직 또는 유효 조직 조건을 충족해야 한다. |
| TPL-S005 | 로컬 검증 | 대상 서비스 소유 조직 담당자 방식은 자격증명 분류에서만 허용하고 여러 서비스 리소스를 포함할 수 있는 접근 정책 분류에서는 거부해야 한다.                                                                                                                                                                                                                                 |

| UIR-S003 | 로컬 검증 | 동기화는 선택된 네임스페이스와 포함 리소스를 기준으로 추가·갱신·정상 복귀·고아 예정 집합을 계산한다. 제외된 기존 리소스는 자동 삭제하지 않고 고아 시각을 기록하며 마지막 동기화 시각을 갱신해야 한다. 고아는 후속 동기화 이후에도 명시적으로 삭제될 때까지 유지해야 한다.                                                                                                                                                                  |
| UIR-S004 | 로컬 검증 | UI 리소스의 실효 활성 상태는 자신과 모든 상위 리소스의 활성·고아 상태를 함께 계산해야 한다. 상위가 비활성 또는 고아면 하위가 활성이어도 노출 가능한 리소스로 반환하지 않아야 한다.                                                                                                                                                                                                                                                         |
| UIR-S005 | 로컬 검증 | 동기화 대상 네임스페이스는 사용자에게 직접 또는 소속 조직·유효 역할·그룹을 통해 부여된 활성 정책의 네임스페이스 리소스로 제한한다. 실제 동기화는 해당 네임스페이스, 동기화 action UI 리소스와 네임스페이스에 종속되지 않는 동기화 API 엔드포인트 허용을 모두 검증해야 한다. 네임스페이스 생성 시 이 세 범주를 묶은 관리자 접근 정책을 시스템 관리자 역할에 자동 부여하고, 선택한 경우 정상 하위 UI 리소스 전체로 원자적으로 갱신해야 한다. |
| UIR-S006 | 로컬 검증 | 존재하지 않거나 비활성인 네임스페이스, 중복 key, 잘못된 lowerCamelCase, 네임스페이스 밖 부모, 누락된 직계 상위와 순환 부모 관계를 거부해야 한다.                                                                                                                                                                                                                                                                                           |
| UIR-S007 | 로컬 검증 | UI 리소스 정책 부여와 요청은 대상이 이미 보유한 리소스와 누락된 리소스를 실효 상태 기준으로 계산해야 한다. 시스템 기본 UI 권한은 개별 메뉴·action 정책 대신 일반 사용자·전문 운영자·네임스페이스 관리자 역할별 정책으로 묶어야 한다.                                                                                                                                                                                                       |

## 9. 운영 서버 연동 범위

다음 항목은 업무 규칙이 아니라 운영 인프라와 연결되는 구현 범위다.

- 인증 공급자 로그인, 서버 세션과 내부 사용자 매핑
- 데이터베이스 영속 저장, 마이그레이션, 트랜잭션과 동시성 제어
- 서버 검색·정렬·페이지네이션 API
- 감사 로그의 보존 기간, 조회 권한과 위변조 방지
- AWS Secrets Manager 및 내부 Credential 발급 API
- 승인자 인증, 반려, 회수, 재상신과 장기 실행 workflow
- 알림 전달 채널, 읽음 상태와 재전송 정책

## 10. 서버 인수 기준

- 존재하지 않거나 권한 없는 사용자, 조직, 역할, 그룹, 서비스, 엔드포인트, 정책, 템플릿 참조를 저장하지 않아야 한다.
- 클라이언트 검증을 우회한 요청에도 동일한 데이터·권한·상태 규칙을 적용해야 한다.
- 관계 변경은 양쪽 query에서 일관된 결과를 반환하고 트랜잭션 실패 시 부분 반영되지 않아야 한다.
- 요청 템플릿의 동적 담당자는 제출 시점의 최신 데이터로 모두 해석되어야 한다.
- 승인과 자격증명 등록은 별도 상태 전이이며 같은 승인 요청으로 자격증명을 두 번 생성할 수 없어야 한다.
- API Key 원문은 허용된 비밀 저장소 외의 DB, 응답, 로그와 오류 추적 데이터에 남지 않아야 한다.
- 권한 판정은 직접·조직·역할·그룹 경로와 거부 우선순위를 모두 적용해야 한다.
- 동시 요청, 재시도와 중복 이벤트가 엔티티나 상태 전이를 중복 생성하지 않아야 한다.
