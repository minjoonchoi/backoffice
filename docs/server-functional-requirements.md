# Backoffice 서버 기능 요구사항

## 1. 문서 정보

| 항목             | 내용                                                                                                |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| 문서 목적        | 백오피스의 데이터 모델, 권한 판정, 상태 전이, 무결성, 영속 저장, 감사 및 외부 연동 규칙을 정의한다. |
| 대상 사용자      | 백엔드 개발자, 프런트엔드 개발자, 아키텍트, 보안 담당자, QA 담당자                                  |
| 기준일           | 2026-08-18                                                                                          |
| UI 기능 요구사항 | [Backoffice UI 기능 요구사항](ui-functional-requirements.md)                                        |
| MVP 이후 범위    | [Backoffice MVP 이후 서버 기능 요구사항](post-mvp-server-functional-requirements.md)                |

이 문서는 클라이언트 구현과 관계없이 서버가 보장해야 하는 업무 규칙의 원본이다. 클라이언트가 동일 규칙을 선검증하더라도 서버는 인증된 요청 주체와 최신 데이터를 기준으로 다시 판정한다.

상태는 다음과 같이 구분한다.

- `MVP 필수`: 화면 노출 여부와 관계없이 MVP의 안전한 조회·변경을 위해 운영 서버가 반드시 제공해야 한다.
- `로컬 검증`: 현재 local API/domain 계층에서 규칙을 검증한다. 운영 서버 구현 완료를 의미하지 않는다.
- `외부 연동`: 운영 환경의 인증, 데이터베이스 또는 외부 시스템 구현이 필요하다.

MVP 필수 기반 규칙은 현재 local 계층의 구현 여부나 화면 노출 여부를 이유로 MVP 이후 범위로 이동하지 않는다. MVP 이후 문서에는 MVP에서 숨긴 전용 UI를 다시 활성화할 때만 필요한 query 또는 command만 둔다.

서버 요구사항 ID는 UI 문서의 도메인 prefix에 `S`를 추가한다. 예를 들어 `USR-S001`은 사용자 서버 규칙이며 관련 UI 요구사항에서 이 ID를 참조한다.

## 2. 공통 서버 요구사항

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                                         |
| -------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| COM-S001 | 로컬 검증 | 모든 command 입력은 신뢰하지 않고 스키마로 검증해야 한다. 실패는 구분 가능한 오류 코드로 반환하고 예외를 성공으로 변환하거나 무시하지 않아야 한다.                                                                                                               |
| COM-S002 | 외부 연동 | 운영 데이터는 데이터베이스에 영속 저장하고 생성·수정·삭제·권한 부여·회수의 주체, 대상, 시각과 결과를 감사 로그로 남겨야 한다.                                                                                                                                    |
| COM-S003 | 로컬 검증 | 인증 사용자와 직접·조직·역할 경유 활성 정책을 기준으로 UI 리소스와 업무 command 권한을 서버에서 검증해야 한다. 권한 정보가 없거나 불완전하면 허용하지 않아야 한다.                                                                                               |
| COM-S004 | 로컬 검증 | 사용자·조직·역할 관계는 중복 저장하지 않아야 하며 연결과 제거 command는 대상 존재 여부와 보호 관계를 검증해야 한다.                                                                                                                                              |
| COM-S005 | MVP 필수  | 목록 query는 허용된 컬럼 조건, 정렬과 최대 20개 단위 페이지네이션을 제공하고 권한 범위가 적용된 전체 개수를 함께 반환해야 한다.                                                                                                                                  |
| COM-S006 | 로컬 검증 | 요청 제출, 승인, 정책 부여·회수, 리소스 생성·폐기와 자격증명 등록 이벤트는 대상 사용자별 알림으로 생성하고 최신 순 조회가 가능해야 한다. 운영 서버는 중복 이벤트 방지와 읽음 상태를 함께 관리해야 한다.                                                          |
| COM-S007 | MVP 필수  | 상태를 변경하는 command는 트랜잭션 경계를 가져야 하며 재시도 또는 동시 요청으로 같은 결과가 중복 생성되지 않도록 멱등성 또는 충돌 검사를 제공해야 한다.                                                                                                          |
| COM-S008 | 외부 연동 | 운영 서버는 인증 공급자의 세션을 검증해 내부 사용자와 연결해야 한다. 유효하지 않은 세션, 퇴직 사용자 또는 알 수 없는 사용자는 보호 리소스에 접근할 수 없어야 한다.                                                                                               |
| COM-S009 | 로컬 검증 | 서버는 프런트엔드 URL을 권한 식별자로 저장하지 않고 네임스페이스와 안정적인 UI 리소스 key를 사용해야 한다. 경로 변경은 권한 데이터 변경을 요구하지 않아야 한다.                                                                                                  |
| COM-S010 | MVP 필수  | 페이지네이션 목록 query는 한 종류의 엔티티와 안정적인 행 스키마만 반환해야 한다. 서로 다른 엔티티를 하나의 union 목록으로 합치지 않고 유형별 query로 분리하며, 감사 이벤트·알림·동기화 작업처럼 자체 공통 엔티티로 모델링된 데이터만 유형 필터를 제공할 수 있다. |

## 3. IAM 데이터와 권한

### 3.1 공통 관계

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                                     |
| -------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| IAM-S001 | 로컬 검증 | 사용자와 조직은 다대다 관계다. 재직·휴직 사용자는 하나 이상의 조직에 소속되고 퇴직 사용자만 무소속일 수 있다.                                                                                                                                                |
| IAM-S002 | 로컬 검증 | 조직은 하나의 상위 조직과 여러 하위 조직을 가질 수 있으며 자기 자신 또는 하위 조직을 상위로 지정하는 순환 관계를 허용하지 않아야 한다.                                                                                                                       |
| IAM-S003 | 로컬 검증 | 역할은 사용자·조직과 각각 다대다 관계이며 직접 부여와 조직 경유 역할을 구분할 수 있어야 한다.                                                                                                                                                                |
| IAM-S005 | 로컬 검증 | 모든 사용자에게 `Backoffice 일반 사용자` 역할을 자동 부여하되 IAM 리소스는 포함하지 않아야 한다. IAM 조회·관리 기능과 그 외 전문 운영 기능은 메뉴별 역할 하드코딩이 아니라 역할에 연결된 유형별 정책으로 관리해야 한다.                                      |
| IAM-S006 | 로컬 검증 | 사용자 조회 시 직접·조직 경유 역할과 소속 조직을 구분해 반환하고 유효 역할과 정책을 계산할 수 있어야 한다.                                                                                                                                                   |
| IAM-S007 | 로컬 검증 | 시스템 기본 `Backoffice IAM 운영자` 역할은 사용자·조직·역할·어플리케이션의 메뉴, 목록·상세 view와 관리 action을 하나의 UI 접근 정책으로 제공해야 한다. 로컬 fixture에서는 개발 1팀에 이 역할을 부여하고 시스템 관리자 역할은 David에게만 직접 부여해야 한다. |

| USR-S005 | 로컬 검증 | 사용자 상세 query는 사용자가 작성한 요청과 그 요청에서 생성된 현재·과거 자격증명을 요청일 역순으로 반환할 수 있어야 한다.                                                                                                         |
| USR-S006 | 로컬 검증 | 조직 관계 제거 전후의 유효 역할·실효 정책·자격증명 조회 범위를 같은 권한 계산 규칙으로 비교해 영향을 반환해야 한다.                                                                                                               |

### 3.5 어플리케이션

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                       |
| -------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| APP-S001 | 로컬 검증 | 어플리케이션은 2~~100자의 고유 이름, 소문자 영문·숫자 단어를 밑줄로 연결한 2~~64자의 고유 snake_case slug, 2~500자의 설명, 소유 조직과 생성 시각을 가진 독립 권한 주체다. 서비스와 자동 1:1 관계를 만들지 않아야 한다.                         |

## 4. 요청 템플릿

| ID       | 상태      | 요구사항                                                                                                                                                                                                                                                                                                                                                                                  |
| -------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TPL-S001 | 로컬 검증 | 템플릿은 고유 이름, `access-policy`·`credential` 분류, 분류에 맞는 처리 유형, 활성 상태, `internal`·`groo` 결재 방식, 처리 단계와 입력 항목을 가진다. 비활성 템플릿은 새 요청에 사용할 수 없어야 한다.                                                                                                                                                                                    |
| TPL-S002 | 로컬 검증 | 내부 결재 템플릿의 실행 단계는 1~12이며 첫 단계는 1, 이후 단계는 같은 번호 또는 1 증가만 허용한다. 같은 실행 단계는 병렬로 해석하고 단계 유형은 요청·승인·합의·참조만 허용한다. Groo 연동 템플릿에는 내부 처리 단계를 저장하지 않아야 한다.                                                                                                                                               |
| TPL-S003 | 로컬 검증 | 입력 항목은 최대 30개, 템플릿 안에서 고유한 소문자 kebab-case key, 표시 이름, 필수 여부와 입력 방식을 가진다. 시스템 연결 값은 종류별 하나만 허용하며 발급 템플릿은 서비스·요청 조직·자격증명 이름·요청 사유를, 교체·폐기 템플릿은 요청 조직·사유를 필수로 가진다.                                                                                                                        |
| TPL-S004 | 로컬 검증 | 내부 결재 템플릿의 고정 사용자·조직은 저장 시 검증하고 요청자, 작성 시 선택 사용자, 요청 조직장·조직과 대상 서비스 소유 조직은 요청 작성 시점의 최신 데이터로 초기 확정해야 한다. 요청자가 요청 조직의 조직장이면 자신이 아닌 재직 조직장이 발견될 때까지 상위 조직을 탐색한다. 해석되지 않은 담당자는 요청자가 명시적으로 유효 사용자·조직으로 교체해야 제출할 수 있다.                  |
| TPL-S005 | 로컬 검증 | 대상 서비스 소유 조직 담당자 방식은 자격증명 분류에서만 허용하고 여러 서비스 리소스를 포함할 수 있는 접근 정책 분류에서는 거부해야 한다.                                                                                                                                                                                                                                                  |
| TPL-S006 | 로컬 검증 | 교체·폐기 내부 결재 템플릿은 요청자 → 요청 조직장 승인 → 대상 서비스 소유 조직 합의의 세 단계만 가진다. 요청자가 요청 조직의 조직장이면 승인자는 가장 가까운 상위 조직의 재직 조직장으로 확정해야 하며, 대상 자격증명과 서비스의 유효성도 검증해야 한다.                                                                                                                                  |
| TPL-S007 | 로컬 검증 | 내부 결재 요청 생성 API는 템플릿에서 초기화한 요청별 결재선 스냅샷을 받아 저장해야 한다. 요청자 첫 단계는 고정하고 후속 단계의 순서·병렬 구성·승인·합의·참조 유형과 사용자·조직 담당자는 수정할 수 있다. 결재 또는 합의 단계가 하나 이상이어야 하며 재직 사용자·유효 조직, 중복 단계 ID와 실행 단계 연속성을 검증해야 한다. 요청별 수정은 템플릿 원본과 다른 요청에 반영하지 않아야 한다. |
| TPL-S008 | 로컬 검증 | 템플릿 복제는 새 식별자와 1버전으로 입력·단계 구성을 복제한다. 수정은 기존 버전 전체 스냅샷을 이력에 저장하고 버전을 증가시키며, 참조 서비스·정책과 진행 중 요청 영향 query 및 최신 데이터 기반 담당자 미리보기 query를 제공해야 한다.                                                                                                                                                    |
| TPL-S009 | 로컬 검증 | Groo 연동 기안 템플릿은 공백 없는 1~200자 Groo 기안문서 ID를 필수로 매핑하고 내부 결재선을 함께 가질 수 없어야 한다. 내부 결재 템플릿에는 Groo 기안문서 ID를 저장하지 않아야 한다.                                                                                                                                                                                                        |
| TPL-S010 | 외부 연동 | Groo 템플릿 요청을 제출할 때 서버가 템플릿의 기안문서 ID로 Groo 기안을 생성하고 Groo가 반환한 고유 요청 ID를 요청에 저장해야 한다. 고유 ID는 요청 간 중복될 수 없으며 외부 기안 생성이 실패하면 내부 요청을 제출 상태로 부분 저장하지 않아야 한다.                                                                                                                                        |

## 6. 서비스와 엔드포인트

## 10. 운영 서버 연동 범위

다음 항목은 업무 규칙이 아니라 운영 인프라와 연결되는 구현 범위다.

- 인증 공급자 로그인, 서버 세션과 내부 사용자 매핑
- 데이터베이스 영속 저장, 마이그레이션, 트랜잭션과 동시성 제어
- 서버 검색·정렬·페이지네이션 API
- 감사 로그의 보존 기간, 조회 권한과 위변조 방지
- AWS Secrets Manager 및 내부 Credential 발급 API
- 승인자 인증, 반려, 회수, 재상신과 장기 실행 workflow
- 알림 전달 채널, 읽음 상태와 재전송 정책

## 11. 서버 인수 기준

- 존재하지 않거나 권한 없는 사용자, 조직, 역할, 어플리케이션, 서비스, 엔드포인트, 정책, 템플릿 참조를 저장하지 않아야 한다.
- 클라이언트 검증을 우회한 요청에도 동일한 데이터·권한·상태 규칙을 적용해야 한다.
- 관계 변경은 양쪽 query에서 일관된 결과를 반환하고 트랜잭션 실패 시 부분 반영되지 않아야 한다.
- 요청 템플릿의 동적 담당자는 제출 시점의 최신 데이터로 모두 해석되어야 한다.
- 승인과 자격증명 등록은 별도 상태 전이이며 같은 승인 요청으로 자격증명을 두 번 생성할 수 없어야 한다.
- API Key 원문은 허용된 비밀 저장소 외의 DB, 응답, 로그와 오류 추적 데이터에 남지 않아야 한다.
- 권한 판정은 직접·조직·역할 경로와 거부 우선순위를 모두 적용해야 한다.
- 동시 요청, 재시도와 중복 이벤트가 엔티티나 상태 전이를 중복 생성하지 않아야 한다.
